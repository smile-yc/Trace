## Context

Trace 已经具备正式工作记录、项目、成果、成长目标、里程碑、能力维度、标签、周报、月报、年报和导出能力。新增能力必须围绕“非正式成长记录”和“光子星月度产出”展开，不能改变现有工作量、项目、日报和报表统计语义。

最重要的产品约束是记录成本：日常记录应能在 5-7 分钟内完成。丰富复盘、证据关联和正式汇报表述应放到周度或月度整理阶段，而不是压到每天填写时完成。

## Goals / Non-Goals

**Goals:**

- 新增独立的成长日志模型，用来记录学习、阅读、技能练习、工具尝试、业余项目、复盘思考、培训交流和政治学习。
- 成长日志默认轻量记录，证据关联和汇报提炼支持后补。
- 成长日志默认不进入正式工作量、项目投入、工时和日报数量统计。
- 新增光子星月度产出工作区，把选中的证据整理成三段式月度汇报。
- 复用现有项目、日报、成果、里程碑、能力维度和报表页面中合适的部分。
- 保持现有 Trace 工作流和统计计算不变。

**Non-Goals:**

- 不替换现有日报、项目、成果、月报、年报或成长目标页面。
- 不在本次变更中实现复杂的光子星评分系统。
- 不实现完整富文本知识库或附件上传系统。
- 不实现团队审批流程。
- 不把系统生成文本视为最终提交稿；光子星月报仍是可编辑草稿。

## Decisions

### Decision 1: 成长日志与正式日报分表存储

成长日志应独立于 `records` 存储。这样可以避免把业余学习、细碎成长动作塞进正式日报，保护现有工作量计算和项目排行，同时又能在成长复盘里看见这些证据。

备选方案：在现有日报中增加“仅成长”分类。这个方案短期更省事，但风险是现有报表、质量检查和导出逻辑普遍把日报当作正式工作证据，容易污染统计。

### Decision 2: 快速记录与后续整理分离

成长日志快速记录只要求日期、标题、动作类型、来源场景和简要记录。能力、汇报范围、产出物、标签和证据关联可以快速填写，也可以后续补充。光子星模块归类和正式汇报表述放到月度工作区处理。

备选方案：每天记录时一次性填写所有光子星字段。这个方案能降低月底整理成本，但会破坏 5-7 分钟日常记录约束。

### Decision 3: 证据关联必须可选且不破坏来源数据

成长日志和光子星月报草稿应通过可选关系引用现有项目、日报、成果和里程碑。选择证据进入汇报时，不应自动修改来源证据。

备选方案：只把来源文本复制进光子星草稿。这个方案简单，但会丢失证据追溯能力，也不利于后续年度复盘。

### Decision 4: 光子星是培养产出工作区，不替代普通月报

光子星月度产出应作为独立工作区存在，可以从普通月报和正式记录中取证据，但不替代现有月报。现有月报继续服务工作复盘；光子星月报服务培养计划汇报。

备选方案：把光子星结构直接塞进现有月报页面。这个方案入口少，但会让普通工作月报变重，也容易混淆“工作复盘”和“培养汇报”。

### Decision 5: 光子星草稿需要持久化

生成的光子星月报应保存为可编辑草稿。重新生成时需要提醒用户，避免覆盖手动修改，或者提供独立预览。

备选方案：每次只即时生成文本，不保存草稿。这个方案实现简单，但无法保留你最终修改后的提交版本。

## Data Model Approach

新增 `growth_journal_entries` 表，建议字段：

- `id`
- `date`
- `title`
- `activityType`
- `sourceContext`
- `abilityDimension`
- `reportScopes`
- `notes`
- `outputType`
- `outputTitle`
- `tags`
- `createTime`
- `updateTime`

新增成长日志到以下对象的可选关系：

- 项目
- 日报
- 成果
- 里程碑

新增光子星月度草稿模型，保存：

- 月份
- 选中的证据引用
- 按固定模块分组的本月工作内容
- 成长收获
- 支持事项
- 生成文本
- 手动编辑状态

存储方式可以是一张草稿表加 JSON 内容，也可以拆成更细的 section/item 表。证据关系建议尽量结构化，汇报正文可以用文本或 JSON 保存。

## UI Approach

日常使用保留两个清晰入口：

- 工作记录：沿用现有正式日报流程。
- 成长日志：新增快速记录入口，用于学习和非正式成长。

成长日志页面优先支持：

- 快速新增
- 本周/本月列表
- 按动作类型、来源场景、能力维度、汇报范围筛选
- 选中记录后提炼为成果或补充证据关联

光子星月度产出工作区包括：

- 月份选择
- 候选证据面板
- 本月工作内容模块
- 成长收获编辑
- 支持事项编辑
- 可编辑的汇报文本

## Frontend Layout And Visual Style

整体前端应保持 Trace 现有“专业工作台”风格：清爽、克制、信息密度适中，服务日常记录和复盘，而不是做成学习打卡 App、校园风成长页、卡通成长树或复杂绩效考核看板。

### 今日记录入口

今日记录区域应提供两个并列入口：

- 记录正式工作：进入现有日报表单。
- 记录学习成长：进入成长日志快速表单。

这个入口的目标是降低选择成本，让用户先判断“这是正式工作，还是学习成长”，而不是一开始面对大量字段。

### 成长日志页面

成长日志页面建议使用“顶部操作 + 左侧筛选 + 右侧列表/摘要”的轻量台账布局：

- 顶部：快速新增、本周、本月、今年、搜索。
- 左侧筛选：类型、来源、能力维度、汇报范围、是否有关联产出。
- 主列表：按日期展示标题、摘要、类型、来源、能力标签、产出物和记录级操作。
- 记录操作：编辑、提炼为成果、加入光子星、补充关联。

成长日志不应以图表为主。图表只能作为辅助摘要，不能压过快速记录和回看列表。

从今日工作台进入成长日志后，页面头部应提供返回今日工作台的快捷按钮。该按钮属于导航辅助操作，放在页面右上角动作区，不在页面中额外创建说明卡片。

### 周报/月报/年报呈现

周期复盘页面应分区展示：

- 正式工作概览：沿用现有项目、工时、工作量、成果和问题闭环展示。
- 成长与学习：展示成长日志数量、代表性学习、新技能/新知识、工具尝试、业余实践和产出物。

成长与学习区域必须与正式工作统计有清晰视觉边界，避免用户误解其会计入工作量。

### 光子星月报页面

光子星月报页面建议使用三栏或宽屏左右结构：

- 左侧：候选证据，按正式工作、成长日志、成果、里程碑分组。
- 中间：月报结构，包含本月工作内容、成长收获、需支持事项。
- 右侧：草稿预览、月度摘要或生成结果。

用户应能从候选证据中选择或加入证据，再分配到“重点项目实战、售前/方案支撑、技术学习与知识沉淀、自主实践、政治进步”等模块。

候选证据不得使用浏览器原生按钮堆叠样式。每条证据应采用 Trace 风格的紧凑证据行：白底、灰边、日期/来源小标签、标题摘要和右侧加入操作。正式工作、成长日志、成果、里程碑之间的区分优先使用小标签和弱色状态点，不使用大面积高饱和背景。

月报结构区应按“工作内容模块、成长收获、支持事项”分段纵向组织。输入框、选择框和按钮不得互相重叠；支持事项使用清晰的表单栅格，并在窄屏降为单列。五个工作内容模块只允许使用轻背景或左侧细线，不能整行大色块铺满。

候选证据区在记录较多时不得把正式工作、成长日志、成果和里程碑合并进同一个总滚动栏。四类候选证据应保持独立分组，每个分组拥有自己的可滚动列表区域，分组标题、条目数量和加入操作必须保持可扫描，避免任一类记录过多时拉长整个页面。

光子星月报应提供明确的月份筛选入口，至少支持本月、上月和任意月份选择。月份筛选只改变候选证据、草稿读取和生成月份，不改变正式工作记录本身。

### 配色和视觉语言

默认延续 Trace 现有蓝白专业风，新增模块使用以下色彩语义：

- 主色：`#2563EB`，用于主要按钮、选中态和正式工作相关重点。
- 成长色：`#16A34A`，用于成长日志、学习沉淀、能力提升。
- 提醒色：`#F59E0B`，用于待整理、需支持事项和月报候选提醒。
- 风险色：`#EF4444`，只用于缺口、错误和强提醒。
- 页面背景：`#F8FAFC`。
- 卡片背景：`#FFFFFF`。
- 边框：`#E5E7EB`。
- 主文本：`#111827`。
- 次文本：`#6B7280`。

模块颜色应克制使用，优先体现在小标签、左侧色条、状态点和轻背景上，不使用大面积高饱和色块。

光子星五个模块建议使用轻量标签区分：

- 重点项目实战：蓝色。
- 售前/方案支撑：青色。
- 技术学习与知识沉淀：绿色。
- 自主实践：少量紫色。
- 政治进步：少量红色，仅用于标签或状态，不做大面积背景。

组件风格延续现有 Trace：

- 卡片圆角控制在 8px 左右。
- 表单和列表保持紧凑。
- 使用小尺寸标签和清晰分组。
- 图标优先使用现有 lucide 风格。
- 不使用大面积渐变、装饰图形、卡通插画、过度阴影或营销页面式 hero。

## Reporting Approach

周报、月报、年报可以增加独立的“成长与学习”区域，用于汇总成长日志。该区域必须在视觉和统计语义上与正式工作指标分开。

光子星月报草稿固定使用三段结构：

1. 本月工作内容（做了什么）
2. 本月成长收获（学到了什么）
3. 需支持事项（需要什么）

第一部分优先保留 3-4 项重点。第二部分保留 3-4 条有证据支撑的成长收获。第三部分保留 1-2 条具体支持事项，并写清预期产出和反馈计划。

## Migration Plan

1. 新增表和字段时使用非破坏性迁移。
2. 不修改现有 records、projects、outcomes、settings、report reviews 和 exports 的语义。
3. 先提供成长日志和光子星草稿的空状态 UI。
4. 有成长日志数据后，再在周报、月报、年报中展示独立成长区域。
5. 回滚时只需隐藏新 UI；现有 Trace 数据不被重写。

## Risks / Trade-offs

- [Risk] 日常记录字段越来越多，导致填写负担上升 -> Mitigation: 默认快速入口只保留必要字段，把增强字段放到整理模式。
- [Risk] 用户误以为成长日志会进入正式工作统计 -> Mitigation: 成长日志页面和报表区域明确标注“成长记录，不计入工作量”。
- [Risk] 生成的光子星文本过于模板化 -> Mitigation: 生成前要求选择证据，生成后保持可编辑。
- [Risk] 证据关系后续维护复杂 -> Mitigation: 所有关联都是可选关系，不强制每天填写。
- [Risk] 光子星工作区和现有月报概念重复 -> Mitigation: 明确区分普通月报是工作复盘，光子星月报是培养计划产出。
